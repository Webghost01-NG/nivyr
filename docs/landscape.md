# Nivyr Competitive Falsification Report

Research cutoff: 2026-10-01. Timeboxed desk and source-code audit. “FACT”, “INFERENCE”, and “UNKNOWN” are used deliberately.

## Executive Verdict

**REPOSITION**

No maintained tool found provides a reusable, TypeScript-first suite that drives real modern shielded Zcash events and asserts an arbitrary application's business state. However, the proposed boundary is much thinner than the thesis implies: ZecKit already leaves a disposable regtest network running for custom downstream test steps, while ztest provides typed Rust controls for validators, indexers, wallets, mining, wallet creation, sends, and explicit sync. **FACT:** a developer can already combine either foundation with Vitest, Playwright, or ordinary HTTP assertions. Nivyr is therefore not falsified by an identical product, but the broad “Layer 3 framework” positioning is weak; the defensible gap is a small, reusable set of payment observation state machines, app adapters, and fault controls built on existing infrastructure. Do not build a competing devnet, wallet, indexer, or general test runner.

## What Would Kill Nivyr

Any one of the following would invalidate the remaining thesis:

1. A maintained ZecKit or ztest package exposes parameterized payment scenarios (partial/over payment, memo mismatch, confirmation count, delayed wallet scan, replay), invokes a caller supplied application adapter, and asserts external business state.
2. Five or more independent maintained payment applications use the same shared harness for real shielded end-to-end tests.
3. A two-day proof shows that ZecKit's existing Action plus 100–200 lines of ordinary Vitest helpers express all target scenarios, including deterministic scan lag, without repeated application-specific plumbing.
4. Intended users say they need reliable local Zcash infrastructure only, since ZecKit, Z3, and ztest are converging on that need.
5. Modern wallets or payment sidecars expose deterministic event injection that makes real shielded transactions irrelevant to application tests.

The audit found no evidence for items 1 or 2. Item 3 remains plausible and is the main reason for **REPOSITION**.

## Layer 1 / Layer 2 / Layer 3 Map

The taxonomy is useful as a responsibility map, but the boundaries are porous. ztest and ZingoLib are Layer 2 tools whose ordinary test code can call an application, so “Layer 3” is not necessarily a separate product category.

| Layer | Question | Tools/evidence | Finding |
|---|---|---|---|
| 1 — Protocol | Does Zcash itself work? | Zebra consensus tests, librustzcash transaction/wallet-backend conformance, Ironwood formal work, zcash tx-tool | Mature, active, Rust-heavy. Not Nivyr's scope. |
| 2 — Infrastructure | Do nodes, indexers and wallets work together? | Z3, ztest, ZecKit, Zaino live tests/testutils, ZingoLib scenarios, Darkside, WebZJS E2E, zcash-devtool | Crowded and converging quickly in 2026. Rebuilding this layer would be duplication. |
| 3 — Application behavior | When a real shielded event occurs, does my application transition correctly? | Application-specific CipherPay/ZGo/BTCPay/zpay/Zink tests; no shared cross-application tool found | The gap is real, but today it is filled with ordinary test code, mocks, and manual testnet checks. The reusable surface has not yet been proven large enough for a standalone framework. |

**FACT:** no discovered maintained package accepts an external app adapter and supplies the requested real-chain business scenarios. **INFERENCE:** Layer 3 exists as a testing concern. **INFERENCE:** it may be only a library-sized extension over Layer 2 rather than a separate framework or service.

## Strongest Competitor

**ZecKit** is the closest competitor by product positioning and intended user.

It already gives downstream developers a disposable regtest cluster, real Orchard sends with memos, block generation, wallet sync, multiple wallets, HTTP endpoints, CI automation, and an `only_setup` mode. Its generated workflow literally leaves a slot for custom test steps. That means ZecKit stops only where application-specific orchestration begins: it has a fixed smoke suite, does not accept an application adapter, does not model expected invoice state, and does not package negative payment scenarios or scan-lag controls for JS users.

The boundary is meaningful as a convenience and correctness library, but not yet as a large standalone platform. If Nivyr needs to own Docker images, a node/indexer/wallet stack, faucet, miner, or generic runner, the boundary disappears and Nivyr should be killed. If it is a small consumer of ZecKit or ztest that contributes missing primitives upstream and standardizes event-to-app assertions, the boundary survives.

## "Why Not Just Use ZecKit + Vitest?"

For the first version, **that is basically enough**.

ZecKit can start the network and leave it up; Vitest can create an invoice over HTTP, call ZecKit's faucet/wallet endpoints, invoke Zebra RPC to mine, and query the application. Correct payment, underpayment, overpayment, expiry, and duplicate handling require little framework code. Calling this combination a new general framework would be packaging, not a defensible technical category.

It becomes insufficient only for repeatable fault boundaries that ZecKit does not expose cleanly: broadcast without mining; mined/indexed without recipient scan; controlled wallet rescan; memo-output inspection; restart/replay; reorg; per-step convergence barriers; and portable adapters for different application APIs/event contracts. Those claims must be proven with a spike before product work. The honest recommendation is therefore **REPOSITION**, with a kill gate: if a thin Vitest helper plus existing ZecKit endpoints expresses all target scenarios reliably, contribute it to ZecKit or publish a small companion package rather than build Nivyr as a framework.

## 10 Hostile Judge Questions

1. **Isn't this just ZecKit plus assertions?**  
   **Response:** Mostly, for the illustrative invoice cases. ZecKit already provisions the real chain/wallet/miner and invites custom downstream steps. No evidence justifies duplicating it. The only defensible remainder is reusable control of observation boundaries plus app adapters. **Objection remains strong.**

2. **Why isn't this a small library or contribution inside ZecKit?**  
   **Response:** No evidence says it should be separate. ZecKit is young, lacks Ironwood, and its API is currently a faucet-oriented HTTP surface, so a decoupled adapter package could support ztest/Z3 too. That is an architectural convenience, not a product moat. **Cannot answer strongly; default to extension/companion.**

3. **Why can't Rust teams use ztest and call their app with `reqwest`?**  
   **Response:** They can. ztest has typed mining, accounts, send, balance, and sync controls, and Zaino demonstrates Ironwood scenarios. Nivyr could improve JS ergonomics and payment semantics, but it would not add fundamental capability. **Objection is valid for Rust teams.**

4. **Are underpayment and overpayment actually hard?**  
   **Response:** No. CipherPay implements them as cumulative integer comparisons plus tolerance. The hard part is producing and observing the shielded event at the desired lifecycle point. Nivyr must not market generic arithmetic as Zcash innovation.

5. **Does memo mismatch matter once every invoice gets a diversified address?**  
   **Response:** Sometimes no. CipherPay's security invariant is address match first, with memo fallback only for legacy invoices. Zink also uses a fresh address per invoice. Memo scenarios matter for shared-address systems such as historical ZGo and for protocols that bind extra data, but they are not universal. **Current thesis overweights memos.**

6. **Don't wallet libraries already solve scanning and sync?**  
   **Response:** They solve wallet correctness and expose sync. They do not prove that a merchant app consumes wallet observations into correct business state. Application audits show mocks/manual checks at that boundary. Still, sidecars such as `zcash-payment-service` narrow the residual problem substantially.

7. **Why would payment processors adopt a generic app interface?**  
   **Response:** Unknown. CipherPay, BTCPay, zpay, ZGo and Zink have different invoice/status/event models. Without two real integrations, an adapter abstraction is speculative. **This is the biggest unresolved product assumption.**

8. **Is the addressable market large enough?**  
   **Response:** Evidence is weak. CipherPay's maintainer publicly described the merchant market as small, and audited repositories have low star counts. Repeated new payment projects show developer activity, not sustained demand for a paid or separately maintained test framework. **Cannot answer strongly.**

9. **Will “real shielded” CI be too slow and flaky?**  
   **Response:** It can be. ZecKit documents multi-minute startup and previously required self-hosted runners; Z3/Zebra/Zaino convergence adds barriers. ztest uses Kubernetes. A useful tool needs cached images, explicit readiness barriers, deterministic mining, and a small scenario set. The audit did not benchmark reliability. **Risk remains open.**

10. **Is Ironwood support a moat?**  
    **Response:** No. Ironwood is a real compatibility fault line—new pool, v6 transactions, new compact fields—and current tools have uneven support. But upstream Zebra, Zaino, ZingoLib and librustzcash are actively absorbing it. Nivyr should test against it, not claim ownership of it.

## Unknowns

- **UNKNOWN:** Whether ZecKit maintainers already plan parameterized downstream application scenarios or Ironwood support outside the inspected public branch/issues.
- **UNKNOWN:** Whether Z3's current Zallet RPC surface can complete all send/memo/multi-wallet flows; the regtest guide demonstrates setup and wallet info, not the complete payment loop.
- **UNKNOWN:** Darkside's complete v6/Ironwood fixture compatibility.

## Final Recommendation

**REPOSITION**

- **Confidence:** HIGH that no maintained identical Layer 3 product was found; MEDIUM in the product recommendation because adoption and implementation size remain untested.
- **Strongest evidence FOR Nivyr:** unrelated payment applications independently use transaction fixtures, mocked lifecycle responses, internal scanner tests, or manual testnet procedures; none uses a shared real-shielded application harness. CipherPay implements almost the exact proposed edge cases in production code without a public automated real-chain suite.
- **Strongest evidence AGAINST Nivyr:** ZecKit + ordinary Vitest already covers the simple cases, while ztest exposes nearly all hard controls in Rust and current Zaino tests prove it across Ironwood. The missing layer may be too small to warrant a standalone framework.
- **Single biggest unresolved assumption:** that multiple applications share enough invoice/event/state semantics—and enough need for deterministic scan/confirmation fault injection—to justify a reusable adapter and scenario API instead of small project-specific tests.

Do not proceed with the current broad framework thesis. If work continues later, the falsifiable target should be a thin experiment over an existing Layer 2 substrate; failure to demonstrate substantial reuse across two structurally different payment applications should end the project.
